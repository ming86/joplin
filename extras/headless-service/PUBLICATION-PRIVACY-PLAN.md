# Publication and privacy cleanup plan

**Status (2026-10-31):** Privacy cleanup, the corrections from independent review, and Worker configuration recovery are complete in the independent clone. The expanded reachable-history audit, source-reference checks, and focused recovery checks passed. The original checkout remains unchanged; nothing has been pushed or deployed.

## Goal and boundaries

Prepare the local `feat/headless-service` work for a future public push by removing personal values, deployment-specific records, and other private operational details from the feature's reachable history. The branch has never been published. The reviewed audits found personal contact information, local paths, deployment diaries, and live infrastructure identifiers in tracked files. A targeted history audit found no confirmed plaintext credentials. That result does not establish that the entire upstream history is free of secrets.

Keep the useful implementation history and the upstream merge. Rewrite only commits unique to the feature; leave upstream commit IDs unchanged. Feature commit IDs will change. Public documentation must provide reachable mapped source references while clearly identifying the original checkouts used by historical validation. The private backup and old-to-new commit map will preserve deployment provenance and the original history for private reference. Do not publish the backup, map, replacement lists, or any private audit output.

Treat SOPS-encrypted configuration and its public age recipient as non-secret project material and retain the existing convention. Git commit addresses already use GitHub's noreply format. Do not rotate credentials or move private keys unless evidence of actual exposure creates that need.

## Work sequence

1. **Preserve recovery material.** Outside the publishable checkout, create a private Git bundle containing the original feature ref and a private record of the original deployment configuration. Verify that the bundle contains the expected feature ref and history before changing anything. Create a disposable clone with its own Git directory and perform the remaining steps there, keeping the original checkout and branch untouched. Store the bundle, backup configuration, replacement lists, and old-to-new map outside the publishable repository. The ignored runtime configuration described below is the intentional exception for local use.

2. **Separate recoverable deployment settings from the public template.** Keep `extras/cloudflare-mcp-worker/wrangler.jsonc` generic, with usable placeholders and the binding names and types required by builds, dry runs, and generated types. Track the full deployment configuration in encrypted `extras/cloudflare-mcp-worker/wrangler.sops.json`, using the same age recipient as `.sops.env`. The `config:restore` script regenerates ignored, owner-only `wrangler.local.jsonc`; `predev` and `predeploy` run it before the existing SOPS `.sops.env` command. Keep `npm run dev` and `npm run deploy` as the everyday commands. Edit the encrypted source with `sops edit wrangler.sops.json`, because restore, development, and deployment replace local-file edits. Save newly provisioned resource IDs through that editor. Manual Wrangler administration, including log tailing and resource management, must run `npm run config:restore` first and select `wrangler.local.jsonc`. Keep type generation, dry runs, and local checks usable without the age key. Document fresh-laptop recovery and the account, resources, and host access that remain external prerequisites.

3. **Clean current content.** Remove account-specific release details from `extras/headless-service/deploy/README.md`, `extras/headless-service/UPSTREAM-UPDATE-PLAN.md`, `extras/headless-service/NOTE-MUTATION-RESULTS-PLAN.md`, `extras/headless-service/SEMANTIC.md`, and `extras/cloudflare-mcp-worker/README.md`. Remove `chatgpt-work/DESKTOP-MCP-PARITY-HANDOFF.md` and `chatgpt-work/SEMANTIC-SEARCH-IMPLEMENTATION-PLAN.md` as operational records from public history, after preserving them privately. Move reusable technical explanations into relevant public documentation only where they remain useful without deployment context. Replace personal values in other audited tracked files, history locations, tests, generated declarations, and messages as applicable. Use reserved example addresses in tests rather than personal contact details. Include artifact-storage destinations in the inventory; personal data is not limited to emails, hostnames and local paths. Keep private replacement lists and audit results outside the public tree.

4. **Rewrite history in the disposable clone.** Use an audited, path- and value-scoped history rewrite to remove the private records and replace sensitive literals. Use the separate clone from step 1 rather than a linked worktree, which shares Git storage and refs with its original repository. Use the private installation of `git-filter-repo`; retain the exact scoped command and resulting map with the private execution evidence. Apply replacements separately to commit messages and include other reachable history text in the audit. Audit the publish ref explicitly: a partial rewrite may retain private refs and unreachable original objects, which must never be included in a public push. Do not blindly replay a range from the current merge base: the graph contains an upstream development merge, and the current merge base is that merge's second parent rather than the original fork point. Preserve the upstream merge and meaningful implementation commits. Private-only documentation commits may disappear, so do not promise an exact retained commit count.

5. **Review the rewritten result before publication.** Confirm that reachable public history, not only the working tree, no longer contains the audited personal values, local paths, deployment diaries, or live infrastructure identifiers. Confirm upstream commit IDs remain unchanged, the upstream merge and meaningful implementation history remain, and only the intended feature history has new commit IDs. Compare the application-code diff and confirm changes are limited to the agreed configuration, documentation, and fixtures. Confirm the publish ref does not include the original private branch, bundle, map, or replacement lists. Run focused existing Worker dry-run, type-generation, and relevant tests for the configuration changes; a full headless-service build or redeploy is not required solely for this privacy cleanup.

6. **Prepare a review branch.** Keep the sanitized work on a local branch, proposed name `fork/headless`, until the user reviews the concrete result. The eventual push should publish only that branch through the normal workflow; do not push all refs or private backup refs. This plan does not authorize publication. Stop after preparing the reviewable local result and obtain separate authorization before any push.
